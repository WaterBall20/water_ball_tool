## 1. Overview

WaterBall Tool is a multi-purpose CLI toolkit written in **Rust (edition 2024)**. It currently provides three core
features:

- **`ff`** — Multi-threaded parallel file finder, emits a JSON file manifest with symlink cycle detection and optional
  per-file hashing
- **`wbfp`** — Custom binary archive format (WaterBall Files Pack): pack, unpack, BLAKE3 hash verification, and a
  read-only TUI browser
- **`mp`** — Terminal music player: audio playback with playlist modes, an interactive ratatui TUI, and a realtime-safe
  audio thread architecture

The repository is a cargo **workspace**: the `water_ball_tool` binary crate (CLI entry, `src/`) depends on the
`water_ball_tool_lib` library crate (`water_ball_tool_lib/src/`), which exposes the reusable modules.

## 4. Workspace: Binary vs Library Crate

```
Cargo.toml                       → [workspace] resolver = "3", members = ["water_ball_tool_lib"]
                                   + [package] "water_ball_tool" (binary, src/)
water_ball_tool_lib/Cargo.toml   → [package] "water_ball_tool_lib" (library)
```

**Key Rules**

- The root package is the binary crate `water_ball_tool`; `main.rs` declares `mod command;` — `command.rs` is
  **private** to the binary crate.
- The library crate `water_ball_tool_lib` exports: `file_finder`, `wb_files_pack`, `tools`, `concurrent_ring`,
  `split_ring_buffer`, `music_play`, and `gakumasu` (gated under `#[cfg(debug_assertions)]` — only compiled in debug
  builds).
- Binary code references library code via crate-name-qualified paths — `water_ball_tool_lib::file_finder`,
  `water_ball_tool_lib::wb_files_pack`, `water_ball_tool_lib::tools`, `water_ball_tool_lib::music_play`, … — **not**
  `crate::file_finder`.
- Both packages share metadata and dependencies through `[workspace.package]` / `[workspace.dependencies]`.

## 6. File Finder (`ff`)

### 6.1 Multi-Threaded Work Queue Model

Architecture: **shared work queue + blocking pop** pattern. The queue is a `ConcurrentRing<DirEntry>` (see §12.1);
there is no separate condition variable or running-thread counter.

```mermaid
flowchart TD
    queue["DirQueue (ConcurrentRing<DirEntry>)"]
    w1["Worker 1"]
    w2["Worker 2"]
    wn["Worker N ... (max_threads)"]
    results["Results (Mutex<HashMap<PathBuf, FileInfo>>)"]

    queue -->|push / pop_wait| w1
    queue --> w2
    queue --> wn
    w1 --> results
    w2 --> results
    wn --> results
```

**Worker lifecycle**

1. On spawn: enter the loop
2. Loop: `pop_wait()` from the queue (blocks while it is empty)
3. A pushed directory wakes one blocked worker
4. Queue empty and no other worker can push → `pop_wait()` returns `WritersClosed` / `AllWaiting` → thread exits

**Progress rate limiting**: fires every 50 files / 10 dirs via `pb.send((delta_files, delta_dirs))`.

**Command-layer thread creation**: the `ff` handler's result-collector, progress-aggregator and hash-worker threads are
created with `thread::Builder::new().name(...).spawn(...)` and spawn failures propagate as errors (the panicking
`std::thread::spawn` is forbidden); taking a worker progress bar that must exist is a logic error and aborts via
`unreachable!`.

### 6.2 Symlink Cycle Detection

Each worker thread maintains an independent **inode chain** (`Vec<InodeKey>`) carried by `DirEntry`:

```rust
struct DirEntry {
    path: PathBuf,
    symlink_chain: Vec<InodeKey>,  // inodes of dirs entered via symlinks on this path
}                                  /
```

**Detection flow**

```mermaid
flowchart TD
    entry["Encounter entry"] --> meta["symlink_metadata() check"]
    meta -->|Regular file| pf["process_file() — record metadata (NO cycle check)"]
    meta -->|Regular dir| push["push to queue — chain unchanged (NO cycle check)"]
    meta -->|Symlink| ps["process_symlink()"]
    ps -->|skip_symlinks=true| skip["skip"]
    ps -->|Target is dir| extract["extract inode → lookup in chain"]
    extract -->|Found| cycle["CYCLE! skip + warn log"]
    extract -->|Not found| append["append inode to chain → push to queue"]
    ps -->|Target is file| pff["process_file() (NO cycle check — files can't contain dirs)"]
    ps -->|Broken| broken["warn log"]
```

**Platform differences**

| Platform | InodeKey type | Extraction method                          |
|----------|---------------|--------------------------------------------|
| Unix     | `u128`        | `(dev << 64) \| ino`                       |
| Windows  | `PathBuf`     | `canonicalize()` fallback to original path |

> **Rationale**: Regular directories cannot form cycles in a normal filesystem; only symlinks can close a loop. This
> keeps the detection mechanism scoped exactly where it matters, with zero overhead on normal files and directories.

### 6.3 Core Data Structures

```rust
pub struct FilesList {
    path: String,                            // Root search path
    data_length: u64,                        // Total data size
    file_count: u64,                         // File count (excl. dirs)
    dir_count: u64,                          // Directory count
    files_list: HashMap<String, FileInfo>,   // Direct children of root
}

pub struct FileInfo {
    name: String,           // Name (without path)
    length: u64,            // File=actual size, Dir=cumulative child total
    modified_time: u128,    // ms since UNIX epoch
    file_kind: FileKind,
}

pub enum FileKind {
    File {
        hash: Option<HashMap<String, String>>,  // Per-file hashes (only when [HASH]... is given)
    },
    Dir(Dir),
}

pub struct Dir {
    files_list: HashMap<String, FileInfo>,  // Direct children
    file_count: u64,                        // Cumulative descendant file count
    dir_count: u64,                         // Cumulative descendant dir count
}
```

### 6.4 Streaming Search API

| Feature               | `search()`                  | `search_stream()`                             |
|-----------------------|-----------------------------|-----------------------------------------------|
| `FilesList` tree      | `Some(results)` — full tree | `None` (skips HashMap)                        |
| `HashMap` (in-memory) | Collected                   | None — zero overhead                          |
| Blocking, one-shot    | Yes                         | No — returns `(JoinHandle, Receiver<...>)`    |
| Used by               | `ff` command                | `wbfp` pack, `ff` hashing (producer-consumer) |

### 6.5 Tree Rebuilding

Parallel scan produces a flat `HashMap<PathBuf, FileInfo>`. `build_tree()` reconstructs the nested `FilesList`:

1. Group all entries by parent path → `HashMap<PathBuf, Vec<PathBuf>>`
2. Iterative stack-based post-order build (Pre/Post state machine with explicit `Fr` frames) — avoids stack overflow on
   deeply nested hierarchies; parent-child linkage uses `rposition()` backward search for correct path matching
3. Directory `length` = sum of all descendant file sizes
4. Directory `file_count`/`dir_count` = cumulative across all subdirectories

### 6.6 Hash Computation

- CLI: the optional multi-value positional `[HASH]...` argument (after `[OUT_PATH]`) accepts `all`, `md5`, `sha256`,
  `sha512`, `sha1`, `blake3`, `blake2b`, `crc32` (aliases `*`, `m5`, `s256`, `s512`, `s1`, `b3`, `b2b`, `crc`).
- Implementation (`command/ff.rs`): `HashTypeS` holds one hasher per selected algorithm and exposes `update`, `reset`,
  and `finalize_reset_str_map` (hex strings), so multiple algorithms share a single read pass.
- `search_stream()` is called with `ff_thread_count = 1` when hashing is enabled; discovered file entries are pushed
  into a `ConcurrentRing`, and `thread_count` hash workers (from `-t/--thread-count` or available parallelism) pop
  entries, read each file with a 10 MiB buffer, compute the hashes, and insert a new `FileInfo` with
  `FileKind::File { hash: Some(map) }` into the result map.
- The main thread aggregates per-worker progress over an mpsc channel (rate-limited to every 10 MiB).
- Selecting MD5/SHA-1 logs an insecurity warning. Every code path (open failure, read failure, EOF mismatch, channel
  disconnect) resets the hashers so the next file starts clean.

## 7. Music Player (`mp`)

**Files**: engine in `water_ball_tool_lib/src/music_play/` (~3,100 lines); terminal front-end in
`src/command/music_play.rs` + `src/command/music_play/` (~850 lines)

### 7.1 Overview

`mp` is a terminal music player. The command:

1. Validates the volume argument and installs the TUI logging subscriber (records go into the panel, see §7.7).
2. Creates `Runtime` (player + playlist + event sinks) and spawns the `mp-scan` thread, which walks `files...`, reads tags
   with `lofty` (directories only accept extensions `lofty` recognizes; an explicitly passed file is always tried) and
   sends `ScanMessage::{Track, Progress, Done}` to the TUI loop.
3. Initializes the terminal and runs `tui::run`: drain logs/scan messages → apply the runtime snapshot → render every
   50 ms. Initialization loads the first track paused: sequential modes do it as soon as the first track arrives,
   `shuffle`/`periodic-shuffle` wait for 5 tracks and fall back to initializing with whatever was found when the scan
   ends. Playback starts only with `-a/--autoplay` (or when the user presses play). Keys: `n` next, `←`/`→` seek
   (5 s per tap; a hold previews and commits on release), space play/pause, `p` pause, `P` play, `+`/`-` volume,
   `:` command mode, `q`/`Esc`/`Ctrl+C` quit.

CLI arguments (`MusicPlayArgs`):

| Argument             | Default           | Purpose                                                                                 |
|----------------------|-------------------|-----------------------------------------------------------------------------------------|
| `files...`           | —                 | Audio files and/or directories to play                                                  |
| `-v, --volume <f32>` | `0.75`            | Initial volume, 0.0–1.0 (values outside this range are rejected with an argument error) |
| `--verbose`          | off               | Verbose output (long option only)                                                       |
| `-a, --autoplay`     | off               | Start playing once the first track is found; without it the first track is loaded paused |
| `-m, --mode <MODE>`  | `sequential-loop` | `sequential-loop`, `sequential`, `repeat-one`, `shuffle`, `periodic-shuffle`            |

### 7.3 Realtime Audio Thread

Data flows from the decode thread → pre-effect ring buffer → pre-effect runtime → split ring buffer (lock-free read
side) → cpal callback → device.

The cpal callback runs in a realtime context and therefore:

- never takes a blocking lock (it uses `try_lock` on the effect chain and the split ring buffer's lock-free reader),
- never invokes `PlayerEventSink` directly,
- never writes logs.

The split ring buffer's lock-free read path publishes `read.pos` and then checks for waiting writers. That check is
bracketed by a `SeqCst` fence on both sides (publisher in `notify_*_after_*`, waiter in `enter_wait`), so "publisher
skipped the wakeup" and "waiter read a stale position" cannot happen together — a missed wakeup would park the peer
forever. Only a fence is used, never a lock, so the callback path stays realtime-safe.

Instead it posts events (`TrackEnded`) and log records with non-blocking `try_send` into the `EventDispatcher`'s
bounded channel (`DISPATCH_CHANNEL_CAPACITY = 1024`). A full channel drops the message and increments the dropped
counter (reported at debug level on stop).

The `player-event-dispatch` thread performs the real work: locking the sink list, invoking `PlayerEventSink::emit`, and
emitting `tracing` events (including stream errors) through the normal logging pipeline.

Transport commands (`PlayCmd::{Play, Pause, Seek, ClearEofBuf}`) travel from the command side to the callback over a
bounded crossbeam channel; accepted commands are reported back on an unbounded channel to the `rx_cmd` thread, which
drives `stream.play()` / `stream.pause()`.

### 7.4 Decoder Runtime & Error Propagation

- The decoder keeps its symphonia engine (format reader + decoder) and its data (track metadata) together in one
  `DecoderSession` stored in a single `Arc<Mutex<Option<DecoderSession>>>`. Track changes replace or take the whole
  session under that one lock, so an "engine present but data missing" state cannot occur. The old split
  `engine`/`data` `Option` pair and its missing-data branch are gone.
- The decoder batches interleaved samples in its internal `out_buf` until it reaches the pre-effect chain's
  `min_input_len_work()` hint (the chain takes the maximum over its effects) before pushing a `Block`. The hint is
  advisory, not a guarantee that smaller inputs produce no output: that depends on the effect, and an effect without
  internal buffering may process every packet; `0` means no accumulation is required. Debug readings include the
  decoder-internal buffer, the decode→pre-effect queue, the pre-effect delay lines and the playback ring.
- `DecoderRuntime::run()` and `PreEffectRuntime::run()` return `Result`; a failed thread spawn aborts `Player::new()`
  with an error instead of being logged and ignored.
- Decode-loop error policy:
    - transient IO errors (see `DecoderRuntime::is_retryable_io_error`, e.g. Windows 1450 `ERROR_NO_SYSTEM_RESOURCES`)
      are retried up to 5 times with a 200 ms delay before being treated as failures;
    - real runtime failures that cannot be retried, or whose retries are exhausted — `next_packet` error, a genuine
      ring-buffer write failure, a failed EOF push, or a fatal (non-frame-level) decode error — emit a `DecoderEvent`
      error, then take the session, clear the pending output buffer and return to the condvar wait; the decode thread
      stays alive, so a later track change plays;
    - the same failures set the atomic `poisoned` flag (`DecoderRuntime::is_poisoned`). A successful
      `DecoderRuntime::set_decoder_path` clears it automatically, so the front-end cannot forget the cleanup and turn a
      later play command into a premature track change;
    - a single-frame `DecodeError` is recoverable: it is reported and the frame is skipped;
    - `WriteRejected` during stop, track change, or seek is normal control flow, not an error.
- The binary front-end consumes decoder error events through a `DecoderEventChannelSink` (channel thread, never inline
  on the decode thread) and pauses playback. The next `play` sees `is_poisoned()` and changes track first, then starts
  playback; the TUI shows the `异常暂停中` state and a red `Error` line in the now-playing block.
- `DecoderRuntime::stop()` records a `send_skip` failure, always joins the decode thread, then returns the first error;
  `Player::try_stop` logs stop failures and continues the remaining shutdown steps.
- The pre-effect runtime thread never exits on a runtime error: a ring error resets the effect chain with the `Skip`
  discontinuity, emits `PreEffectRuntimeEventErrorKind::Runtime`, backs off 10 ms and keeps consuming (a closed write
  side therefore parks instead of spinning); a hard output-write error is reported the same way and the block is
  dropped. Only the `stop` flag ends the loop. The binary logs these events through a
  `PreEffectRuntimeEventChannelSink` (informational — playback may continue). The chain lock is released before the
  blocking output-ring write, so the UI can snapshot effect metadata even while paused with a full ring.
- Event-channel sink constructors (`PlayerEventChannelSink::create`, `DecoderEventChannelSink::create`,
  `PreEffectRuntimeEventChannelSink::create`) return `Result`; direct sinks construct infallibly. `Player::new()` and
  `Runtime::new()` propagate sink and thread spawn failures.

### 7.5 Shutdown (`Player::try_stop`)

`try_stop()` is idempotent and reclaims every thread in a fixed order:

1. Shut the watchdog down (`WatchNotify::shutdown`), so it cannot restart a thread during shutdown.
2. Pause the audio stream and clear `is_playing`, so no new events are produced.
3. Stop the pre-effect runtime — its `reject_waiting_writers` wakes producers blocked in `push_wait`, preventing a join
   deadlock.
4. Stop the decoder thread.
5. Stop the event dispatch thread (`Stop` message + join).
6. Join the `rx_cmd` thread via the handle stored in the player.
7. Join the watchdog thread.

Failures at any step are logged, not propagated; `Runtime::run_stop` additionally joins the UI thread.

### 7.6 Crash watchdog (`watchdog.rs`)

- A watched thread (`decoder-runtime`, `pre-effect-running`) owns a `ThreadExitGuard` inside its closure. On `Drop`
  (panic unwind included) the guard sets its slot bit in `WatchNotify` and wakes the single watchdog thread on a
  `Condvar` — no `JoinHandle::is_finished()` polling, no second thread.
- `Player::new` injects the notifier into both runtimes before `run()` and spawns `player-watchdog`.
- On exit the watchdog pauses playback (it never resumes automatically), sets the decoder poison flag so `Play`
  recovers by changing track, and restarts the dead thread (`run()` reclaims the finished `JoinHandle` first). For the
  pre-effect runtime the whole effect chain is rebuilt through the factory registered by `Player::new` before the
  restart, because the old effects may already be poisoned.
- `try_stop` shuts the watchdog down before stopping the threads and joins it last, so a normal shutdown never triggers
  a restart.

### 8.1 Overall Architecture

WBFP uses a **three-layer architecture**


### 8.4 Manifest Data Block — A/B Dual-Block Mechanism

**File**: `water_ball_tool_lib/src/wb_files_pack/data.rs` (1762 lines — the largest single module)

All index data (Attribute, PackStruct, PackFileMetadata, DataPosList) is stored in `ManifestDataBlock` instances.

**A/B block structure**

```
┌──────── A Block ────────┬──────── B Block ────────     ┐
│ len(8) │ ver(4) │ hash(8) │ data(...) │ ver(4) │ ...   │
└─────────────────────────┴─────────────────────────     ┘
──────────────────────────────────────────────────────────
        Entire block = aligned to multiples of DATA_BLOCK_LEN (128B)
```

**Atomic update flow**

1. Read both half-blocks, extract version numbers from each
2. Write to the half-block with the **lower** version (`ver + 1`)
3. The other half-block remains untouched
4. Crash after partial write → at least one complete version survives

**Read flow**

1. Check A-block head-tail version match (fast integrity check)
2. Check B-block the same way
3. Pick the half with the higher version that passes validation

**Block size calculation**

```
block_len = ceil((24 + data_len) × 2 / DATA_BLOCK_LEN) × DATA_BLOCK_LEN
```

**Version wrapping**

```rust
fn next_ver(ver: u32) -> u32 {
    if ver == u32::MAX { 1 } else { ver + 1 }
}

// Uses wrapping subtraction to correctly handle u32 rollover
fn ver_is_older(a: u32, b: u32) -> bool {
    a != b && b.wrapping_sub(a) < a.wrapping_sub(b)
}
```

### 8.5 Space Allocation & Garbage Collection

**Core file**: `water_ball_tool_lib/src/wb_files_pack/pack_io.rs` (402 lines) — PackIO layer

**Space allocation `get_file_pos(length)`**

```
1. Align length to DATA_BLOCK_LEN (128B) boundary
2. Try free list first (empty_data_list):
   └─ Exact match → remove from list, return
   └─ Larger than needed → split: allocate front, keep remainder
3. No suitable free block → extend file: return (file.len, length)
```

**Data allocation**
Pass 1
`get_pos_contiguous`
`MAX_DATA_SEGMENTS`(16)

- Known size (`alloc_size(Some(len))`, e.g. length known from search) allocates
  exactly at 128B alignment via `get_file_pos`, matching the pack's global
  alignment rule with no waste. Unknown size (`alloc_size(None)`, default)
  allocates via 4MiB-aligned `get_data_file_pos_multi` (initial `create_file_raw`)
  reusing free fragments first: Pass 1 single-block first-fit (`get_pos_gc`) →
  Pass 2 contiguous chain of physically adjacent fragments (`get_pos_contiguous`)
  → Pass 3 largest-first accumulation (`get_pos_biggest`); the `empty_data_list`
  order is never changed; extend-file fallback when fragments are insufficient.
  Segments are counted against the virtual file's data segment list (`data_pos_list` existing + new), capped at
  `MAX_DATA_SEGMENTS` (16); over-limit
  allocations are rejected with an error (no partial writes). Fragments are
  batch-sorted and merged into `empty_data_list` by `file_gc` (during `save_all`)
  before they participate in reuse. `alloc_size` is ignored when opening an
  existing file (never shrinks an existing allocation). Manifest data always
  uses 128B-aligned `get_file_pos`.

**Garbage collection**

```
Stage 1 — Staging (file_gc_add):
   ├─ PackFileHandle drops → manager → file_gc_add buffers into gc_data_pos_list

Stage 2 — Merging (file_gc):
   ├─ Append staging items to empty_data_list, then batch sort_unstable_by_key(pos)
   │  O((K+M) log(K+M))
   │  batch sort replaces the previous insertion sort
   ├─ Single-pass merge adjacent: pos1 + len1 == pos2 → merge into one block
   └─ Write updated empty data list
```

**GC trigger points**

- `WBFPManager.save_all()` → `file_gc()` + `manifest_file_gc()`
- File resize-down or overwrite → `PackFileHandle::commit_data()` on drop

**Overwrite strategies**

| Strategy  | Passes | Description                                                     |
|-----------|--------|-----------------------------------------------------------------|
| `Zero`    | 1      | Single pass of 0x00                                             |

> `child_locked_count` on `PackStruct` tracks how many descendant files have active virtual-file handles. A directory
> can only be deleted/erased or renamed/moved when `child_locked_count == 0`. `rename` rejects the operation while the
> file itself is locked; a read-only `PackVirtualFile` also holds the handle. `rename` never relocates an entry: `from`
> and `to` must share the same parent. `move_entry` requires a different parent; it may also change the leaf name,
> rejects moving a directory into its own subtree, and updates the cumulative `file_count`/`dir_count`/`len` of every
> affected ancestor on both the source and destination chains. The destination `PackStruct` is written before the

- `Arc<Mutex<>>` for thread safety — multiple `PackVirtualFile` instances can operate concurrently

- `ManagerSync` is `Clone` — multiple holders share the same pack reference

### 8.9 Virtual File I/O — PackVirtualFile + PackFileHandle

**PackVirtualFile** (`pack_io/pack_file.rs`, 210+ lines) — renamed from `PackFileWR`:

- Implements `Read + Write + Seek` traits with **access mode enforcement**
- Holds `Arc<Mutex<PackFileHandle>>`
- Tracks `pos` (current read/write position) + `AccessMode` (Read/Write/ReadWrite)
- All operations delegated to `PackFileHandle`
- Opened via `VirtualFileOpenOptions` builder pattern (std::fs::File-compatible)
- `get_len()` returns `u64` (not `Result<u64>`); `get_modified()` returns `u128` (not `Result<u128>`) — internal lock
  acquisition no longer produces a recoverable error
- Mutex poison recovery uses `std::sync::PoisonError::into_inner` throughout

**PackFileHandle** (`pack_io/file_handle.rs`, 493 lines — the most complex single file

```
Responsibilities
    1. Virtual file position management (sparse file support)
    2. Allocation: DataPosList-managed (position, length) list
    3. set_len: grow → auto-allocate new blocks; shrink → release excess → GC
    4. write: map virtual position → real file offset → pack_io.write
    5. read:  map virtual position → real file offset → pack_io.read
    6. commit_data (Drop): compute hash → write back metadata → release pre-allocated space

```

**Position mapping cache**: `temp_pos_index` + `temp_pos_this_len` avoids traversing the entire DataPosList on every
read/write.

**Drop behavior**: `PackFileHandle.drop()` auto-invokes `commit_data()`:

1. Compute and persist file hash
2. Release pre-allocated but unused space (via `set_len(metadata_len)`)
3. Return metadata to `WBFPManager.file_metadata_update()`

`PackFileHandle` captures `path_list` when it opens and `commit_data()` uses that path to locate the item for the
metadata write-back. Renaming or relocating an open entry is therefore forbidden: `WBFPManager::rename` returns
`PackFileError::Lock` while the file, or any descendant file of a directory, is open. Read-only handles count too.

### 8.15 Worker Threads & Error Policy

- Pack/unpack/hash-verify worker threads and the pack search/copy helper threads are created with
  `thread::Builder::new().name(...).spawn(...)`; a spawn failure is propagated (`PackFileError` / `io::Error`) instead
  of panicking (`std::thread::spawn` panics when the OS cannot create a thread).
- Exhausting the per-worker progress-bar pool is an invariant violation and aborts via `unreachable!`.
- In `manager/file_ops.rs`, `manager/metadata.rs`, and `pack_io/file_handle.rs`, invariant violations (missing metadata
  while a handle exists, non-file metadata reached through a file handle, …) abort via `unreachable!`.
- Genuine runtime failures are returned, never converted into `unreachable!`: for example
  `open_virtual_file`/`create_virtual_file` receiving a directory path returns `PackFileError`, and spawn/I/O failures
  propagate as errors.

### 8.16 TUI Mode

**Files**: `src/command/wbfp/` (`classic.rs`, `common.rs`, `events.rs`, `ops.rs`, `tui.rs`, `tui/app.rs`,
`tui/ui.rs`, `tui/browse.rs`)

- **Routing**: `wbfp::run` selects the TUI when stdout and stdin are terminals and `--no-tui` is absent; otherwise it calls the
  classic `indicatif` path. `wbfp::commands` always takes the classic path (tests use it). `browse` has no classic
  equivalent and requires an interactive terminal. Without a subcommand the file manager is TUI-only: the pack path is
  optional (`wbfp <pack>` opens it immediately, bare `wbfp` starts with the middle pane hidden), and `--no-tui`/non-TTY
  input are rejected. `wbfp browse <pack>` remains the read-only single-pane browser; pack/unpack/verify keep their
  existing single-pane layout.
- **Layout**: Manager mode has three panes — local filesystem, pack, preview. At width >= 110 three panes are shown
  (30/40/30); at >= 80 the preview folds and local/pack remain (35/65); below 80 the focused pane stays alone. With no
  pack, the middle pane is omitted: local/preview at >= 80, local only below that. Preview folds before the local pane;
  the pack pane is never folded while a pack is open. A copy/move picker places a same-kind target pane next to the
  source (right of a local source, left of a pack source) and folds to the target pane below 80. While a transfer job
  runs, the job card is pinned to the right: three panes at >= 110, active list + job card at >= 80, job card alone
  below that. Subcommand modes keep the old single list + preview layout.
- **State**: `App` groups `ui` (mode, title, pack info, logs, quit flags, error), `nav` (primary pane; pack in manager
  mode and the only pane in subcommands), `local_nav` (manager's filesystem pane), `focus` (`Local`/`Pack`), `pending`
  (narrow cross-namespace transfer awaiting `v`), `picker` (same-namespace destination pane), `rename` (inline editor),
  `delete` (confirmation target), the job sender/handles, and `jobs`. Popups remain a `Window` enum with a `Confirm`
  variant for deletion. Pack files on disk are probed by header, never by extension; a probe result is stored in
  `Entry.pack_version` and rendered as a magenta `◆`.
- **Navigation**: `ManagerSync` lazily loads one pack directory at a time; the local pane uses `std::fs`. `Tab` switches
  focus, `Enter` enters a directory or opens a probed local pack, `Ctrl+W` closes the pack. Mouse hit-testing selects
  the pane under the cursor; during a picker or pending transfer only the target pane is hit-testable. Select/
  double-click/wheel is shared with `mp` through `command/tui_input.rs`. On Windows the TUI uses the same VT input path
  as `mp`; if mouse capture cannot start it continues keyboard-only.
- **Copy/move**: `y`/`x` copy/move the focused entry to the other namespace. When both lists are visible they start the
  transfer immediately; otherwise the app switches focus to the other list, shows the operation and source path in the
  header, and waits for `v` (`Esc` cancels). `c`/`m` copy/move inside the same namespace: the source list becomes
  read-only, focus moves to a same-kind target pane, and `v` confirms. A directory cannot enter its own subtree; such
  rows are rejected while navigating and rendered red. The destination name must not exist; directory copies preserve
  empty directories; a move copies first and deletes the source only when every file succeeded. Same-volume local moves
  and in-pack moves use `fs::rename`/`move_entry` (metadata only).
- **Rename/delete**: `r` opens an inline editor prefilled with the current leaf name and fully selected; `Enter`
  commits, `Esc` cancels. Local renames use `fs::rename`, pack renames use `ManagerSync::rename` (same directory only).
  `Del` requests a `y/n` confirmation before removing the entry.
- **Jobs**: `ops::spawn` runs pack/unpack/verify and copy/move transfers on background threads and sends
  `JobEvent::{Dir, File, Start, Progress, Done, Total, Finished}` over a bounded mpsc channel.
  `app::App::apply_event` updates row statuses and the task card. `JobSpec::Transfer` uses the recommended worker count
  (`common::get_thread_count(None)`), discovers the tree, copies files in parallel, and deletes the source after a
  successful move. Unpack/verify open one read-only `ManagerSync` and share a clone with the job: the pack's `.lock`
  rejects a second open in the same process, so the UI cannot keep a separate handle. Reads serialize on the manager
  lock; the UI stays responsive because each directory load is short.
- **Status aggregation**: directory rows aggregate descendant file states incrementally (`failed` > `warning` >
  `running/pending` > `done`); a parent is never shown done while a child is unfinished. Unpack/verify empty directories
  receive an explicit `Done` event; pack does not emit directory events because it never copies directories, so an empty
  source directory stays neutral instead of spinning. Hash verify writes nothing, so its task card has no output field.
- **Task list**: `JobEvent::{Start, Progress, Done}` carries per-file `done/total`. `App` keeps two bounded queues:
  `active_tasks` (current files, newest first) and `done_tasks` (finished, below active). The preview pane renders active
  rows first. Workers only enqueue events on an unbounded channel (progress is rate-limited to 4–10 MiB); the UI never
  stats or reads files for the task list, so it cannot slow the job.
- **Column alignment**: file-list and task rows use fixed display-width columns (`unicode-width`), fixed progress-bar
  and percent widths, and a fixed-height job summary. Sizes split into a right-aligned numeric column and a fixed-width
  unit column (`B`/`KiB`/...), so the one-cell `B` cannot shift the number. Small files completing quickly cannot make
  columns or the task area jump.
- **Progress**: the TUI never writes `indicatif` output while in the alternate screen. `common::copy_file_into_pack` and
  `common::extract_pack_file_to_disk` are shared with the classic path; TUI workers report per-file progress and a
  rate-limited global `Total` instead. The job card and task rows use the same `command::eighth_block_bar` as
  `mp`, so both TUIs resolve progress to 1/8 of a cell. The job card draws the bar on its own row and the label below
  it, so the text never masks progress; write-optimization skips are reported as `Done`, not warnings.
- **Shutdown**: `Esc` cancels a picker, pending transfer, rename, or delete confirmation before any write starts; a
  running job is not interruptible. During a job, `q`/`Ctrl+C` sets `quit_after_job`; the loop exits only after
  `Finished`, so a pack write is never abandoned mid-flight. Mouse capture is released by a Drop guard and the terminal
  is restored on every exit path, matching `mp`.
- **Logging**: the TUI installs `music_play::tui::channel_writer::init_logging("wbfp")`; logs go to a bounded channel and
  the `F12` debug popup. The classic path keeps `multi_progress_init`.

**Key design**:

- `TerminalWriter` buffers output per line and enqueues it into a bounded channel (capacity 1024) drained by the

  paused or the console is stalled), while file logging stays synchronous and lossless.
- Every `EnvFilter` is built by `log_filter(level)` = `<level>,lofty=warn`: `tracing-subscriber`'s default
  `tracing-log` bridge feeds lofty's per-block `log` records into this writer, and each line clears and redraws every
  bar, so third-party debug records are capped at `warn`.

- Release log file path: `<ProjectDirs data_local_dir>/<crate>/logs/<module>/<module>-<YYYY-MM-DD_HH-MM-SS>.log` (module

## 12. Ring Buffer Modules

**Files**: `water_ball_tool_lib/src/concurrent_ring.rs`, `water_ball_tool_lib/src/split_ring_buffer/`

### 12.1 `concurrent_ring`

`ConcurrentRing<T>` is a concurrent, initializable ring buffer used as the producer-consumer queue between
search/decoder threads and worker threads. Blocking operations fail fast instead of blocking forever: every blocking
method (`push_wait` / `write_wait` / `write_all` vs `pop_wait` / `read_wait` / `read_exact`) registers the calling
handle's direction, `Clone`/`Drop` keep a per-direction handle count, and once the last handle of one direction is
dropped the opposite side gets `ReadersClosed` / `WritersClosed` (mirroring `split_ring_buffer`'s peer-closed
`CannotWait`). There is no separate reader/writer handle type and no manual close/reopen call; a ring whose handles
never called a blocking method is never reported closed.

`wake_blocked_readers` actively wakes a blocked `pop_wait` without touching the buffer: it sets a sticky flag under the
wait lock and notifies the readers. The woken call returns `ReadWoken` and leaves all queued data intact; the flag
survives a wake issued before the reader starts waiting, so the pre-effect thread can be woken for a control command
even when no audio block arrives. The wake is one-shot and intended for a single reader (the pre-effect input ring).

### 12.2 `split_ring_buffer`

A split read/write ring buffer where each end can independently be locked or lock-free (`locked_ring_buffer`,
`unlocked_read_locked_write_ring_buffer`, …); the audio callback uses the lock-free reader. `write_all` returns a
dedicated `WriteAllError { written, kind }`: `Interrupted` comes from the non-destructive `wake_blocked_writers` (the
buffer is intact, so the caller may resume from `written`), `Rejected` comes from `reject_pending_writers` (the buffer
was cleared, so the prefix is gone), and `PeerClosed` means the reader disappeared. `wake_blocked_writers` bumps a
separate wake epoch and only notifies; `reject_pending_writers` keeps the existing clear-and-reject semantics.
`LockedWriter::resize` /
`UnlockedWriter::resize` (Copy only) change the logical capacity: growing past the physical allocation allocates new
A/B buffers, blocks new writers and waits for in-flight writers (readers keep running and only see "no data" during
the tiny swap window), copies the live range into the new A at the same logical positions, swaps the buffers and
retires the old A until no operation is in flight. Shrink or grow-within-allocation only updates the capacity
atomically; data already written past the new capacity is kept, so `len()` may temporarily exceed `capacity()` and
writers stall until the reader drains.

## 15. Design Decisions & Tradeoffs

### File Finder

| Decision                                | Rationale                                                                                 |
|-----------------------------------------|-------------------------------------------------------------------------------------------|
| Per-thread inode chain (not global map) | Simpler, lock-free; cycles are rare and usually on a single path                          |
| Flat HashMap + post-scan tree rebuild   | More efficient than maintaining nested tree during scanning                               |
| No cycle check on regular files/dirs    | Filesystem cannot form cycles with normal directories; detection only needed for symlinks |
| Windows uses PathBuf as InodeKey        | Cannot reliably get (dev, ino) on Windows; canonicalize as best approximation             |

### WBFP

| Decision                              | Rationale                                                                                                          |
|---------------------------------------|--------------------------------------------------------------------------------------------------------------------|
| A/B dual-block instead of WAL         | Simpler implementation; no separate log file or replay logic                                                       |
| BLAKE3 truncated to 8 bytes           | Storage-constrained; collision probability negligible at 8 bytes                                                   |
| PackIO implements both Read+Write     | Centralized I/O; easy separated/embedded mode switching                                                            |
| Separate manifest on by default       | Core pack file needs no modification, reducing corruption risk                                                     |
| Lazy directory structure loading      | Avoids parsing entire pack on open; load-on-demand                                                                 |
| Progressive (throttled) save          | Prevents data loss from power failure during long pack ops                                                         |
| PID lock file + sysinfo               | More reliable than pure file locks; detects stale locks                                                            |
| `Arc<Mutex<>>` instead of Actor model | Simpler implementation; direct state sharing, no message passing                                                   |
| PackFileHandle commits on Drop        | Guarantees persistence even if caller forgets to close                                                             |
| `child_locked_count` per PackStruct   | Directory safety: inc on file handle creation, dec on unlock; delete/erase blocked when > 0                        |
| Delete vs Erase as separate APIs      | Delete is fast (metadata-only I/O, GC data without overwrite); Erase overwrites every byte on disk before removal  |
| DoD 5220 writes each pass to disk     | All three passes (0x00, 0xFF, random) perform independent disk writes — not just in-memory buffer churn            |
| Erase offsets advance per chunk       | Multi-block data overwrite seeks to `pos + write_len` on every pass; otherwise only the first chunk is overwritten |

### Music Player

| Decision                                 | Rationale                                                                                            |
|------------------------------------------|------------------------------------------------------------------------------------------------------|
| Realtime callback posts, never emits     | No locking / sink calls / logging on the audio thread — avoids jitter, priority inversion, underruns |
| Bounded dispatch channel (1024)          | `try_send` never blocks the realtime thread; overflow is counted and reported instead of stalling    |
| Dedicated `player-event-dispatch` thread | All sink locking/emission and tracing output happen outside the audio callback                       |
| Split ring buffer for audio data         | Lock-free read side for the callback; writer side stays locked for the producer                      |
| Fixed stop order in `try_stop`           | Pausing the stream first, then pre-effect → decoder → dispatcher → `rx_cmd`, prevents join deadlocks |
| Single `DecoderSession` lock             | Engine + metadata are swapped/taken as a pair; an unpaired state cannot occur                        |
| `run()` returns spawn errors             | Player initialization aborts on thread-spawn failure instead of running without that thread          |
| Logic errors use `unreachable!`          | Runtime failures are returned/reported; only broken invariants abort                                 |
| `debug-no-audio` feature                 | Lets playback-control logic be debugged without audio hardware or real sample flow                   |

### Overall

| Decision                                 | Rationale                                                                             |
|------------------------------------------|---------------------------------------------------------------------------------------|
| Workspace (binary + library crate)       | Library logic in `water_ball_tool_lib`; CLI-only code in the root binary package      |
| Thread creation via `thread::Builder`    | Command-layer spawn failures are returned as errors; `std::thread::spawn` would panic |
| Logic errors abort via `unreachable!`    | Broken invariants abort; genuine runtime failures are returned or reported            |
| Crate-name-qualified paths in command.rs | `command.rs` is in binary crate, not the library                                      |
| `PackFileError` impls `From` both ways   | Enables `?` operator + Read/Write/Seek trait impls                                    |
| Bilingual comments throughout            | Chinese developer, English code; comments in both languages                           |
