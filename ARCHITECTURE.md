## 1. Overview

WaterBall Tool is a multi-purpose CLI toolkit written in **Rust (edition 2024)**. It currently provides three core
features:

- **`ff`** — Multi-threaded parallel file finder, emits a JSON file manifest with symlink cycle detection and optional
  per-file hashing
- **`wbfp`** — Custom binary archive format (WaterBall Files Pack): pack, unpack, and BLAKE3 hash verification
- **`mp`** — Terminal music player: audio playback with playlist modes, stdin controls, and a realtime-safe audio
  thread architecture (`tui/` interface is still WIP)

The repository is a cargo **workspace**: the `water_ball_tool` binary crate (CLI entry, `src/`) depends on the
`water_ball_tool_lib` library crate (`water_ball_tool_lib/src/`), which exposes the reusable modules.

## 4. Workspace: Binary vs Library Crate

```
Cargo.toml                       → [workspace] resolver = "3", members = ["water_ball_tool_lib"]
                                   + [package] "water_ball_tool" (binary, src/)
water_ball_tool_lib/Cargo.toml   → [package] "water_ball_tool_lib" (library)
```

**Key Rules**

- The root package is the binary crate `water_ball_tool`; `main.rs` declares `mod command;` — `command.rs` is
  **private** to the binary crate.
- The library crate `water_ball_tool_lib` exports: `file_finder`, `wb_files_pack`, `tools`, `concurrent_ring`,
  `split_ring_buffer`, and `gakumasu` (gated under `#[cfg(debug_assertions)]` — only compiled in debug builds).
- Binary code references library code via crate-name-qualified paths — `water_ball_tool_lib::file_finder`,
  `water_ball_tool_lib::wb_files_pack`, `water_ball_tool_lib::tools`, … — **not** `crate::file_finder`.
- Both packages share metadata and dependencies through `[workspace.package]` / `[workspace.dependencies]`.

## 6. File Finder (`ff`)

### 6.1 Multi-Threaded Work Queue Model

Architecture: **shared work queue + condition variable** pattern.

```mermaid
flowchart TD
    queue["DirQueue (Mutex<VecDeque<DirEntry>>)"]
    w1["Worker 1"]
    w2["Worker 2"]
    wn["Worker N ... (max_threads)"]
    results["Results (Mutex<HashMap<PathBuf, FileInfo>>)"]

    queue -->|pop_front / push_back| w1
    queue --> w2
    queue --> wn
    w1 --> results
    w2 --> results
    wn --> results
```

**Worker lifecycle**

1. On spawn: `running_count` incremented
2. Loop: `pop_front()` from queue
3. Queue empty: `running_count` decremented, check if zero
    - `running_count == 0` → `condvar.notify_all()`, thread exits
    - Otherwise → `condvar.wait()`, recheck on wake
4. Woken: `running_count` incremented, process popped task

**Progress rate limiting**: fires every 50 files / 10 dirs via `pb.send((delta_files, delta_dirs))`.

**Command-layer thread creation**: the `ff` handler's result-collector, progress-aggregator and hash-worker threads are
created with `thread::Builder::new().name(...).spawn(...)` and spawn failures propagate as errors (the panicking
`std::thread::spawn` is forbidden); taking a worker progress bar that must exist is a logic error and aborts via
`unreachable!`.

### 6.2 Symlink Cycle Detection

Each worker thread maintains an independent **inode chain** (`Vec<InodeKey>`) carried by `DirEntry`:

```rust
struct DirEntry {
    path: PathBuf,
    symlink_chain: Vec<InodeKey>,  // inodes of dirs entered via symlinks on this path
}                                  /
```

**Detection flow**

```mermaid
flowchart TD
    entry["Encounter entry"] --> meta["symlink_metadata() check"]
    meta -->|Regular file| pf["process_file() — record metadata (NO cycle check)"]
    meta -->|Regular dir| push["push to queue — chain unchanged (NO cycle check)"]
    meta -->|Symlink| ps["process_symlink()"]
    ps -->|skip_symlinks=true| skip["skip"]
    ps -->|Target is dir| extract["extract inode → lookup in chain"]
    extract -->|Found| cycle["CYCLE! skip + warn log"]
    extract -->|Not found| append["append inode to chain → push to queue"]
    ps -->|Target is file| pff["process_file() (NO cycle check — files can't contain dirs)"]
    ps -->|Broken| broken["warn log"]
```

**Platform differences**

| Platform | InodeKey type | Extraction method                          |
|----------|---------------|--------------------------------------------|
| Unix     | `u128`        | `(dev << 64) \| ino`                       |
| Windows  | `PathBuf`     | `canonicalize()` fallback to original path |

> **Rationale**: Regular directories cannot form cycles in a normal filesystem; only symlinks can close a loop. This
> keeps the detection mechanism scoped exactly where it matters, with zero overhead on normal files and directories.

### 6.3 Core Data Structures

```rust
pub struct FilesList {
    path: String,                            // Root search path
    data_length: u64,                        // Total data size
    file_count: u64,                         // File count (excl. dirs)
    dir_count: u64,                          // Directory count
    files_list: HashMap<String, FileInfo>,   // Direct children of root
}

pub struct FileInfo {
    name: String,           // Name (without path)
    length: u64,            // File=actual size, Dir=cumulative child total
    modified_time: u128,    // ms since UNIX epoch
    file_kind: FileKind,
}

pub enum FileKind {
    File {
        hash: Option<HashMap<String, String>>,  // Per-file hashes (only when [HASH]... is given)
    },
    Dir(Dir),
}

pub struct Dir {
    files_list: HashMap<String, FileInfo>,  // Direct children
    file_count: u64,                        // Cumulative descendant file count
    dir_count: u64,                         // Cumulative descendant dir count
}
```

### 6.4 Streaming Search API

| Feature               | `search()`                  | `search_stream()`                             |
|-----------------------|-----------------------------|-----------------------------------------------|
| `FilesList` tree      | `Some(results)` — full tree | `None` (skips HashMap)                        |
| `HashMap` (in-memory) | Collected                   | None — zero overhead                          |
| Blocking, one-shot    | Yes                         | No — returns `(JoinHandle, Receiver<...>)`    |
| Used by               | `ff` command                | `wbfp` pack, `ff` hashing (producer-consumer) |

### 6.5 Tree Rebuilding

Parallel scan produces a flat `HashMap<PathBuf, FileInfo>`. `build_tree()` reconstructs the nested `FilesList`:

1. Group all entries by parent path → `HashMap<PathBuf, Vec<PathBuf>>`
2. Iterative stack-based post-order build (Pre/Post state machine with explicit `Fr` frames) — avoids stack overflow on
   deeply nested hierarchies; parent-child linkage uses `rposition()` backward search for correct path matching
3. Directory `length` = sum of all descendant file sizes
4. Directory `file_count`/`dir_count` = cumulative across all subdirectories

### 6.6 Hash Computation

- CLI: the optional multi-value positional `[HASH]...` argument (after `[OUT_PATH]`) accepts `all`, `md5`, `sha256`,
  `sha512`, `sha1`, `blake3`, `blake2b`, `crc32` (aliases `*`, `m5`, `s256`, `s512`, `s1`, `b3`, `b2b`, `crc`).
- Implementation (`command/ff.rs`): `HashTypeS` holds one hasher per selected algorithm and exposes `update`, `reset`,
  and `finalize_reset_str_map` (hex strings), so multiple algorithms share a single read pass.
- `search_stream()` is called with `ff_thread_count = 1` when hashing is enabled; discovered file entries are pushed
  into a `ConcurrentRing`, and `thread_count` hash workers (from `-t/--thread-count` or available parallelism) pop
  entries, read each file with a 10 MiB buffer, compute the hashes, and insert a new `FileInfo` with
  `FileKind::File { hash: Some(map) }` into the result map.
- The main thread aggregates per-worker progress over an mpsc channel (rate-limited to every 10 MiB).
- Selecting MD5/SHA-1 logs an insecurity warning. Every code path (open failure, read failure, EOF mismatch, channel
  disconnect) resets the hashers so the next file starts clean.

## 7. Music Player (`mp`)

**Files**: `src/command/music_play.rs` + `src/command/music_play/*.rs` (~4,900 lines total)

### 7.1 Overview

`mp` is a terminal music player. The command:

1. Collects tracks from the positional `files...` paths (directories are walked recursively); tags and duration come
   from `lofty`, and tracks whose metadata cannot be read are logged and skipped.
2. Builds a `PlayList` with the selected loop mode and creates a `Runtime`.
3. Starts playback and then reads commands from stdin until `exit`: `next`/`n`, `Play`/`P`, `pause`/`p`, `exit`.

CLI arguments (`MusicPlayArgs`):

| Argument             | Default           | Purpose                                                                                 |
|----------------------|-------------------|-----------------------------------------------------------------------------------------|
| `files...`           | —                 | Audio files and/or directories to play                                                  |
| `-v, --volume <f32>` | `0.75`            | Initial volume, 0.0–1.0 (values outside this range are rejected with an argument error) |
| `--verbose`          | off               | Verbose output (long option only)                                                       |
| `-m, --mode <MODE>`  | `sequential-loop` | `sequential-loop`, `sequential`, `repeat-one`, `shuffle`, `periodic-shuffle`            |

### 7.2 Modules

| Module                   | Responsibility                                                                                                                  |
|--------------------------|---------------------------------------------------------------------------------------------------------------------------------|
| `player.rs`              | cpal output stream, `PlayCmd` transport, volume/position atomics, event sinks, `Player::try_stop`                               |
| `decoder_runtime.rs`     | symphonia decode thread: probes/seeks the file, decodes audio into the pre-effect ring buffer; owns the paired `DecoderSession` |
| `effect.rs`              | `PostEffect`/`PreEffect` traits, `AudioFormat`, `PlayCmd`, effect chain                                                         |
| `effect/runtime.rs`      | Locked pre-effect runtime thread (event sinks, stop/reject handling)                                                            |
| `effect/resampler.rs`    | rubato FFT resampler to the output device sample rate                                                                           |
| `effect/cross_bridge.rs` | Crossfade bridging between tracks                                                                                               |
| `effect/fade.rs`         | Fade in/out and pause/resume transport handling                                                                                 |
| `play_list.rs`           | `Track` list, loop modes, shuffle queues, next-track selection                                                                  |
| `runtime.rs`             | Orchestration: track advance on `TrackEnded`, UI refresh thread, event consumers, stop                                          |
| `event_dispatch.rs`      | Dedicated dispatch thread for realtime-callback events and logs                                                                 |
| `tools.rs`               | `TimeMetrics` / `DurationAccumulator` profiling counters                                                                        |
| `tui/`                   | Terminal UI (`app.rs`, `ui.rs`, `channel_writer.rs`) — **WIP, not wired into the command**                                      |

### 7.3 Realtime Audio Thread

Data flows from the decode thread → pre-effect ring buffer → pre-effect runtime → split ring buffer (lock-free read
side) → cpal callback → device.

The cpal callback runs in a realtime context and therefore:

- never takes a blocking lock (it uses `try_lock` on the effect chain and the split ring buffer's lock-free reader),
- never invokes `PlayerEventSink` directly,
- never writes logs.

Instead it posts events (`TrackEnded`) and log records with non-blocking `try_send` into the `EventDispatcher`'s
bounded channel (`DISPATCH_CHANNEL_CAPACITY = 1024`). A full channel drops the message and increments the dropped
counter (reported at debug level on stop).

The `player-event-dispatch` thread performs the real work: locking the sink list, invoking `PlayerEventSink::emit`, and
emitting `tracing` events (including stream errors) through the normal logging pipeline.

Transport commands (`PlayCmd::{Play, Pause, Seek, ClearEofBuf}`) travel from the command side to the callback over a
bounded crossbeam channel; accepted commands are reported back on an unbounded channel to the `rx_cmd` thread, which
drives `stream.play()` / `stream.pause()`.

### 7.4 Decoder Runtime & Error Propagation

- The decoder keeps its symphonia engine (format reader + decoder) and its data (track metadata) together in one
  `DecoderSession` stored in a single `Arc<Mutex<Option<DecoderSession>>>`. Track changes replace or take the whole
  session under that one lock, so an "engine present but data missing" state cannot occur. The old split
  `engine`/`data` `Option` pair and its missing-data branch are gone.
- `DecoderRuntime::run()` and `PreEffectRuntime::run()` return `Result`; a failed thread spawn aborts `Player::new()`
  with an error instead of being logged and ignored.
- Decode-loop error policy:
    - real runtime failures — `next_packet` error, a genuine ring-buffer write failure, a failed EOF push, or a fatal
      (non-frame-level) decode error — emit a `DecoderEvent` error and stop the decode thread;
    - a single-frame `DecodeError` is recoverable: it is reported and the frame is skipped;
    - `WriteRejected` during stop, track change, or seek is normal control flow, not an error.
- `DecoderRuntime::stop()` records a `send_skip` failure, always joins the decode thread, then returns the first error;
  `Player::try_stop` logs stop failures and continues the remaining shutdown steps.
- Event-channel sink constructors (`PlayerEventChannelSink::new`, `DecoderEventChannelSink::new`,
  `PreEffectRuntimeEventChannelSink::new`) return `std::io::Result`; direct sinks construct infallibly. `Player::new()`
  and `Runtime::create()` propagate sink and thread spawn failures.

### 7.5 Shutdown (`Player::try_stop`)

`try_stop()` is idempotent and reclaims every thread in a fixed order:

1. Pause the audio stream and clear `is_playing`, so no new events are produced.
2. Stop the pre-effect runtime — its `reject_waiting_writers` wakes producers blocked in `push_wait`, preventing a join
   deadlock.
3. Stop the decoder thread.
4. Stop the event dispatch thread (`Stop` message + join).
5. Join the `rx_cmd` thread via the handle stored in the player.

Failures at any step are logged, not propagated; `Runtime::run_stop` additionally joins the UI thread.

## 8. WaterBall Files Pack (`wbfp`)

**Files**: `water_ball_tool_lib/src/wb_files_pack/*.rs` (~6,000+ lines total)

### 8.1 Overall Architecture

WBFP uses a **three-layer architecture**

```mermaid
flowchart TD
    L1["ManagerSync (public API layer)<br/>Arc&lt;Mutex&lt;WBFPManager&gt;&gt; + Arc&lt;Mutex&lt;PackIO&gt;&gt;<br/>Thread-safe; all external access here"]
    L2["WBFPManager (business logic layer)<br/>Pack lifecycle, file ops, tree, locks, save"]
    L3["PackIO (low-level I/O layer)<br/>File read/write, space allocation, GC merging<br/>Underlying: File (Rust std)"]
    L4["ManifestDataBlock (atomic block layer)<br/>A/B dual-block atomic updates, BLAKE3 hash,<br/>version management"]
    L1 --> L2 --> L3 --> L4
```

### 8.2 Binary Format

Full specification at `docs/en_US/wb_files_pack/manifest-data.md`. Summary:

### 8.3 Core Data Structures

    manifest_file_len: u64,                    // Manifest file length

### 8.4 Manifest Data Block — A/B Dual-Block Mechanism

**File**: `water_ball_tool_lib/src/wb_files_pack/data.rs` (1762 lines — the largest single module)

All index data (Attribute, PackStruct, PackFileMetadata, DataPosList) is stored in `ManifestDataBlock` instances.

**A/B block structure**

```
┌──────── A Block ────────┬──────── B Block ────────     ┐
│ len(8) │ ver(4) │ hash(8) │ data(...) │ ver(4) │ ...   │
└─────────────────────────┴─────────────────────────     ┘
──────────────────────────────────────────────────────────
        Entire block = aligned to multiples of DATA_BLOCK_LEN (128B)
```

**Atomic update flow**

1. Read both half-blocks, extract version numbers from each
2. Write to the half-block with the **lower** version (`ver + 1`)
3. The other half-block remains untouched
4. Crash after partial write → at least one complete version survives

**Read flow**

1. Check A-block head-tail version match (fast integrity check)
2. Check B-block the same way
3. Pick the half with the higher version that passes validation

**Block size calculation**

```
block_len = ceil((24 + data_len) × 2 / DATA_BLOCK_LEN) × DATA_BLOCK_LEN
```

**Version wrapping**

```rust
fn next_ver(ver: u32) -> u32 {
    if ver == u32::MAX { 1 } else { ver + 1 }
}

// Uses wrapping subtraction to correctly handle u32 rollover
fn ver_is_older(a: u32, b: u32) -> bool {
    a != b && b.wrapping_sub(a) < a.wrapping_sub(b)
}
```

### 8.5 Space Allocation & Garbage Collection

**Core file**: `water_ball_tool_lib/src/wb_files_pack/pack_io.rs` (402 lines) — PackIO layer

**Space allocation `get_file_pos(length)`**

```
1. Align length to DATA_BLOCK_LEN (128B) boundary
2. Try free list first (empty_data_list):
   └─ Exact match → remove from list, return
   └─ Larger than needed → split: allocate front, keep remainder
3. No suitable free block → extend file: return (file.len, length)
```

**Data allocation**
Pass 1
`get_pos_contiguous`
`MAX_DATA_SEGMENTS`(16)

- Known size (`alloc_size(Some(len))`, e.g. length known from search) allocates
  exactly at 128B alignment via `get_file_pos`, matching the pack's global
  alignment rule with no waste. Unknown size (`alloc_size(None)`, default)
  allocates via 4MiB-aligned `get_data_file_pos_multi` (initial `create_file_raw`)
  reusing free fragments first: Pass 1 single-block first-fit (`get_pos_gc`) →
  Pass 2 contiguous chain of physically adjacent fragments (`get_pos_contiguous`)
  → Pass 3 largest-first accumulation (`get_pos_biggest`); the `empty_data_list`
  order is never changed; extend-file fallback when fragments are insufficient.
  Segments are counted against the virtual file's data segment list (`data_pos_list` existing + new), capped at
  `MAX_DATA_SEGMENTS` (16); over-limit
  allocations are rejected with an error (no partial writes). Fragments are
  batch-sorted and merged into `empty_data_list` by `file_gc` (during `save_all`)
  before they participate in reuse. `alloc_size` is ignored when opening an
  existing file (never shrinks an existing allocation). Manifest data always
  uses 128B-aligned `get_file_pos`.

**Garbage collection**

```
Stage 1 — Staging (file_gc_add):
   ├─ PackFileHandle drops → manager → file_gc_add buffers into gc_data_pos_list

Stage 2 — Merging (file_gc):
   ├─ Append staging items to empty_data_list, then batch sort_unstable_by_key(pos)
   │  O((K+M) log(K+M))
   │  batch sort replaces the previous insertion sort
   ├─ Single-pass merge adjacent: pos1 + len1 == pos2 → merge into one block
   └─ Write updated empty data list
```

**GC trigger points**

- `WBFPManager.save_all()` → `file_gc()` + `manifest_file_gc()`
- File resize-down or overwrite → `PackFileHandle::commit_data()` on drop

### 8.9 Virtual File I/O — PackVirtualFile + PackFileHandle

**PackVirtualFile** (`pack_io/file.rs`, 210+ lines) — renamed from `PackFileWR`:

- Implements `Read + Write + Seek` traits with **access mode enforcement**
- Holds `Arc<Mutex<PackFileHandle>>`
- Tracks `pos` (current read/write position) + `AccessMode` (Read/Write/ReadWrite)
- All operations delegated to `PackFileHandle`
- Opened via `VirtualFileOpenOptions` builder pattern (std::fs::File-compatible)

**PackFileHandle** (`pack_io/file_handle.rs`, 493 lines — the most complex single file

```
Responsibilities
    1. Virtual file position management (sparse file support)
    2. Allocation: DataPosList-managed (position, length) list
    3. set_len: grow → auto-allocate new blocks; shrink → release excess → GC
    4. write: map virtual position → real file offset → pack_io.write
    5. read:  map virtual position → real file offset → pack_io.read
    6. commit_data (Drop): compute hash → write back metadata → release pre-allocated space

```

**Position mapping cache**: `temp_pos_index` + `temp_pos_this_len` avoids traversing the entire DataPosList on every
read/write.

**Drop behavior**: `PackFileHandle.drop()` auto-invokes `commit_data()`:

1. Compute and persist file hash
2. Release pre-allocated but unused space (via `set_len(metadata_len)`)
3. Return metadata to `WBFPManager.file_metadata_update()`

### 8.15 Worker Threads & Error Policy

- Pack/unpack/hash-verify worker threads and the pack search/copy helper threads are created with
  `thread::Builder::new().name(...).spawn(...)`; a spawn failure is propagated (`PackFileError` / `io::Error`) instead
  of panicking (`std::thread::spawn` panics when the OS cannot create a thread).
- Exhausting the per-worker progress-bar pool is an invariant violation and aborts via `unreachable!`.
- In `manager/file_ops.rs`, `manager/metadata.rs`, and `pack_io/file_handle.rs`, invariant violations (missing metadata
  while a handle exists, non-file metadata reached through a file handle, …) abort via `unreachable!`.
- Genuine runtime failures are returned, never converted into `unreachable!`: for example
  `open_virtual_file`/`create_virtual_file` receiving a directory path returns `PackFileError`, and spawn/I/O failures
  propagate as errors.

## 14. Design Decisions & Tradeoffs

### File Finder

| Decision                                | Rationale                                                                                 |
|-----------------------------------------|-------------------------------------------------------------------------------------------|
| Per-thread inode chain (not global map) | Simpler, lock-free; cycles are rare and usually on a single path                          |
| Flat HashMap + post-scan tree rebuild   | More efficient than maintaining nested tree during scanning                               |
| No cycle check on regular files/dirs    | Filesystem cannot form cycles with normal directories; detection only needed for symlinks |
| Windows uses PathBuf as InodeKey        | Cannot reliably get (dev, ino) on Windows; canonicalize as best approximation             |

### WBFP

| Decision                              | Rationale                                                                                                          |
|---------------------------------------|--------------------------------------------------------------------------------------------------------------------|
| A/B dual-block instead of WAL         | Simpler implementation; no separate log file or replay logic                                                       |
| BLAKE3 truncated to 8 bytes           | Storage-constrained; collision probability negligible at 8 bytes                                                   |
| PackIO implements both Read+Write     | Centralized I/O; easy separated/embedded mode switching                                                            |
| Separate manifest on by default       | Core pack file needs no modification, reducing corruption risk                                                     |
| Lazy directory structure loading      | Avoids parsing entire pack on open; load-on-demand                                                                 |
| Progressive (throttled) save          | Prevents data loss from power failure during long pack ops                                                         |
| PID lock file + sysinfo               | More reliable than pure file locks; detects stale locks                                                            |
| `Arc<Mutex<>>` instead of Actor model | Simpler implementation; direct state sharing, no message passing                                                   |
| PackFileHandle commits on Drop        | Guarantees persistence even if caller forgets to close                                                             |
| `child_locked_count` per PackStruct   | Directory safety: inc on file handle creation, dec on unlock; delete/erase blocked when > 0                        |
| Delete vs Erase as separate APIs      | Delete is fast (metadata-only I/O, GC data without overwrite); Erase overwrites every byte on disk before removal  |
| DoD 5220 writes each pass to disk     | All three passes (0x00, 0xFF, random) perform independent disk writes — not just in-memory buffer churn            |
| Erase offsets advance per chunk       | Multi-block data overwrite seeks to `pos + write_len` on every pass; otherwise only the first chunk is overwritten |

### Music Player

| Decision                                 | Rationale                                                                                            |
|------------------------------------------|------------------------------------------------------------------------------------------------------|
| Realtime callback posts, never emits     | No locking / sink calls / logging on the audio thread — avoids jitter, priority inversion, underruns |
| Bounded dispatch channel (1024)          | `try_send` never blocks the realtime thread; overflow is counted and reported instead of stalling    |
| Dedicated `player-event-dispatch` thread | All sink locking/emission and tracing output happen outside the audio callback                       |
| Split ring buffer for audio data         | Lock-free read side for the callback; writer side stays locked for the producer                      |
| Fixed stop order in `try_stop`           | Pausing the stream first, then pre-effect → decoder → dispatcher → `rx_cmd`, prevents join deadlocks |
| Single `DecoderSession` lock             | Engine + metadata are swapped/taken as a pair; an unpaired state cannot occur                        |
| `run()` returns spawn errors             | Player initialization aborts on thread-spawn failure instead of running without that thread          |
| Logic errors use `unreachable!`          | Runtime failures are returned/reported; only broken invariants abort                                 |
| `debug-no-audio` feature                 | Lets playback-control logic be debugged without audio hardware or real sample flow                   |

### Overall

| Decision                                 | Rationale                                                                             |
|------------------------------------------|---------------------------------------------------------------------------------------|
| Workspace (binary + library crate)       | Library logic in `water_ball_tool_lib`; CLI-only code in the root binary package      |
| Thread creation via `thread::Builder`    | Command-layer spawn failures are returned as errors; `std::thread::spawn` would panic |
| Logic errors abort via `unreachable!`    | Broken invariants abort; genuine runtime failures are returned or reported            |
| Crate-name-qualified paths in command.rs | `command.rs` is in binary crate, not the library                                      |
| `PackFileError` impls `From` both ways   | Enables `?` operator + Read/Write/Seek trait impls                                    |
| Bilingual comments throughout            | Chinese developer, English code; comments in both languages                           |
