## 1. Overview

> 概述：WaterBall Tool 是一个用 Rust (edition 2024) 编写的多合一 CLI 工具，目前提供两个核心功能。

WaterBall Tool is a multi-purpose CLI toolkit written in **Rust (edition 2024)**. It currently provides two core features:

- **`ff`** — Multi-threaded parallel file finder, emits a JSON file manifest with symlink cycle detection
  > 多线程并行文件搜索器，输出 JSON 格式文件清单，支持符号链接循环检测
- **`wbfp`** — Custom binary archive format (WaterBall Files Pack): pack, unpack, and BLAKE3 hash verification
  > 自定义二进制归档格式：打包、解包、BLAKE3 哈希校验

The project follows the standard Rust **binary crate + library crate** split: the binary crate handles CLI entry, the library crate exposes reusable modules.

> 项目遵循标准的 Rust binary crate + library crate 模式：二进制 crate 负责 CLI 入口，library crate 暴露可重用模块。

## 4. Binary vs Library Crate

> 二进制与库 crate 关系

```
src/main.rs       → binary crate   "water_ball_tool"
src/lib.rs        → library crate  "water_ball_tool"
```

**Key Rules** / 关键规则:

- `main.rs` declares `mod command;` — `command.rs` is **private** to the binary crate
  > `command.rs` 是二进制 crate 私有的
- `command.rs` references library code via crate-name-qualified paths — `water_ball_tool::file_finder`, `water_ball_tool::wb_files_pack` — **not** `crate::file_finder`
  > `command.rs` 使用 crate 名限定路径引用库代码，而非 `crate::`
- `lib.rs` exports public modules: `file_finder`, `wb_files_pack`, `tools`, `gakumasu`
  > `lib.rs` 导出四个公共模块

**Dependency Flow** / 依赖流向:

```
Binary Crate (main.rs)
    ↓ references by crate name / 通过 crate 名引用
Library Crate (lib.rs)
    ├── pub mod file_finder
    ├── pub mod wb_files_pack
    ├── pub mod tools
    └── pub mod gakumasu
```

## 6. File Finder (`ff`)

### 6.1 Multi-Threaded Work Queue Model

> 多线程工作队列模型

Architecture: **shared work queue + condition variable** pattern.

```
                    ┌─────────────────────┐
                    │   DirQueue (Mutex<   │
                    │   VecDeque<DirEntry>>)│
                    └──────┬──────────────┘
                           │ pop_front / push_back
            ┌──────────────┼──────────────┐
            ▼              ▼              ▼
        ┌──────┐      ┌──────┐      ┌──────┐
        │Worker│      │Worker│      │Worker│  ... (max_threads)
        │  1   │      │  2   │      │  N   │
        └──┬───┘      └──┬───┘      └──┬───┘
           │              │              │
           ▼              ▼              ▼
        ┌──────────────────────────────────────┐
        │  Results (Mutex<HashMap<PathBuf,       │
        │  FileInfo>>)                           │
        └──────────────────────────────────────┘
```

**Worker lifecycle** / 工作线程生命周期:

1. On spawn: `running_count` incremented / 启动时递增计数
2. Loop: `pop_front()` from queue / 循环从队列取任务
3. Queue empty: `running_count` decremented, check if zero
   - `running_count == 0` → `condvar.notify_all()`, thread exits / 通知所有线程退出
   - Otherwise → `condvar.wait()`, recheck on wake / 等待新任务
4. Woken: `running_count` incremented, process popped task / 被唤醒后处理任务

**Progress rate limiting**: fires every 50 files / 10 dirs via `pb.send((delta_files, delta_dirs))`.

> 进度限频：每 50 文件或 10 目录触发一次进度更新。

### 6.2 Symlink Cycle Detection

> 符号链接循环检测

Each worker thread maintains an independent **inode chain** (`Vec<InodeKey>`) carried by `DirEntry`:

> 每个线程独立维护一个 inode 链，由 `DirEntry` 携带：

```rust
struct DirEntry {
    path: PathBuf,
    symlink_chain: Vec<InodeKey>,  // inodes of dirs entered via symlinks on this path
}                                  // 从根到此目录经过的符号链接 inode 列表
```

**Detection flow** / 检测流程:

```
Encounter entry → symlink_metadata() check
  ├─ Regular file  → process_file() — record metadata (NO cycle check)
  │   普通文件 → 记录元数据（不检测循环）
  ├─ Regular dir   → push to queue — chain unchanged (NO cycle check)
  │   普通目录 → 推入队列（链不变，不检测循环）
  └─ Symlink       → process_symlink()
       ├─ skip_symlinks=true → skip / 跳过
       ├─ Target is dir  → extract inode → lookup in chain
       │   目标为目录 → 提取 inode → 链中查找
       │   ├─ Found  → CYCLE! skip + warn log / 找到 → 循环！跳过
       │   └─ Not found → append inode to chain → push to queue
       │       未找到 → 附加到链 → 推入队列
       ├─ Target is file → process_file() (NO cycle check — files can't contain dirs)
       │   目标为文件 → 处理文件（不检测循环 — 文件不能包含目录）
       └─ Broken → warn log / 断开 → 警告日志
```

**Platform differences** / 平台差异:

| Platform | InodeKey type | Extraction method | 获取方式 |
|---|---|---|---|
| Unix | `u128` | `(dev << 64) \| ino` from `MetadataExt` |
| Windows | `PathBuf` | `canonicalize()` fallback to original path | 回退到原始路径 |

> **Rationale**: Regular directories cannot form cycles in a normal filesystem; only symlinks can close a loop. This keeps the detection mechanism scoped exactly where it matters, with zero overhead on normal files and directories.
> **设计理由**：普通目录在正常文件系统中无法构成循环；只有符号链接才可能形成闭环。检测范围精确限定，普通文件和目录零额外开销。

> 流式搜索 API

|---|---|---|

### 6.5 Tree Rebuilding

> 树形重建

Parallel scan produces a flat `HashMap<PathBuf, FileInfo>`. `build_tree()` reconstructs the nested `FilesList`:

> 并行扫描产生扁平 HashMap，`build_tree()` 将其还原为嵌套树：

1. Group all entries by parent path → `HashMap<PathBuf, Vec<PathBuf>>`
2. Iterative stack-based post-order build (Pre/Post state machine with explicit `Fr` frames) — avoids stack overflow on deeply nested hierarchies; parent-child linkage uses `rposition()` backward search for correct path matching
3. Directory `length` = sum of all descendant file sizes
4. Directory `file_count`/`dir_count` = cumulative across all subdirectories

### 7.4 Manifest Data Block — A/B Dual-Block Mechanism

> 清单数据块 A/B 双块机制

**File**: `src/wb_files_pack/data.rs` (1762 lines — the largest single module) / 最大单文件

All index data (Attribute, PackStruct, PackFileMetadata, DataPosList) is stored in `ManifestDataBlock` instances.

> 所有索引数据均存储在 `ManifestDataBlock` 实例中。

**A/B block structure** / A/B 双块结构:

```
┌──────── A Block ────────┬──────── B Block ────────┐
│ len(8) │ ver(4) │ hash(8) │ data(...) │ ver(4) │ ... │
└─────────────────────────┴─────────────────────────┘
─────────────────────────────────────────────────────────
        Entire block = aligned to multiples of DATA_BLOCK_LEN (128B)
        整块 = 对齐到 DATA_BLOCK_LEN (128B) 的倍数
```

**Atomic update flow** / 原子更新流程:

1. Read both half-blocks, extract version numbers from each
2. Write to the half-block with the **lower** version (`ver + 1`) / 写入版本号较小的那个半块
3. The other half-block remains untouched / 另一个半块不受影响
4. Crash after partial write → at least one complete version survives / 崩溃后至少保留一个完整版本

**Read flow** / 读取流程:

1. Check A-block head-tail version match (fast integrity check) / 快速完整性校验
2. Check B-block the same way
3. Pick the half with the higher version that passes validation / 取版本号较大且校验通过的块

**Block size calculation** / 块大小计算:

```
block_len = ceil((24 + data_len) × 2 / DATA_BLOCK_LEN) × DATA_BLOCK_LEN
```

**Version wrapping** / 版本号环绕:

```rust
fn next_ver(ver: u32) -> u32 {
    if ver == u32::MAX { 1 } else { ver + 1 }
}

// Uses wrapping subtraction to correctly handle u32 rollover / 环绕减法正确处理溢出
fn ver_is_older(a: u32, b: u32) -> bool {
    a != b && b.wrapping_sub(a) < a.wrapping_sub(b)
}
```

**Testing conventions** / 测试约定:

- Slow tests marked `#[ignore = "longtime"]`, skipped via `cargo test` (默认跳过)。CI 主分支 push 时使用 `--include-ignored` 全量运行。
  > 慢测试标记 `#[ignore = "longtime"]`
- Test temp dir: `./temp/test/` (gitignored) / 测试临时目录
- Tests using `indicatif::MultiProgress` must call `crate::init_global_logging(&mp)` first
  > 使用 MultiProgress 的测试必须先初始化日志
- `TestTool::remove_test_pack_files(path)` for pack file test cleanup
  > 清理 .pack / .wbm / .lock
- Cross-platform tests use `#[cfg(unix)]` / `#[cfg(windows)]` for compilation gating
  > 跨平台条件编译

## 13. Design Decisions & Tradeoffs

> 设计决策与权衡

### File Finder / 文件搜索器

| Decision | Rationale | 理由 |
|---|---|---|
| Per-thread inode chain (not global map) | Simpler, lock-free; cycles are rare and usually on a single path | 更简单，无锁；循环通常发生在同一路径上 |
| Flat HashMap + post-scan tree rebuild | More efficient than maintaining nested tree during scanning | 比扫描时维护嵌套树更高效 |
| No cycle check on regular files/dirs | Filesystem cannot form cycles with normal directories; detection only needed for symlinks | 文件系统本身不会形成普通目录循环 |
| Windows uses PathBuf as InodeKey | Cannot reliably get (dev, ino) on Windows; canonicalize as best approximation | Windows 无法可靠获取 inode；canonicalize 为近似 |

### WBFP / 水球包文件

| Decision | Rationale | 理由 |
|---|---|---|
| A/B dual-block instead of WAL | Simpler implementation; no separate log file or replay logic | 比 WAL 更简单，无额外日志文件 |
| BLAKE3 truncated to 8 bytes | Storage-constrained; collision probability negligible at 8 bytes | 存储空间有限，8 字节碰撞概率极低 |
| PackIO implements both Read+Write | Centralized I/O; easy separated/embedded mode switching | 集中抽象层，易切换分离/嵌入模式 |
| Separate manifest on by default | Core pack file needs no modification, reducing corruption risk | .pack 无需修改，降低损坏风险 |
| Lazy directory structure loading | Avoids parsing entire pack on open; load-on-demand | 避免启动时全量解析，按需加载 |
| Progressive (throttled) save | Prevents data loss from power failure during long pack ops | 防长时间打包时断电丢失数据 |
| PID lock file + sysinfo | More reliable than pure file locks; detects stale locks | 比纯文件锁更可靠，可检测残留锁 |
| `Arc<Mutex<>>` instead of Actor model | Simpler implementation; direct state sharing, no message passing | 简化实现，直接状态共享 |
| PackFileHandle commits on Drop | Guarantees persistence even if caller forgets to close | 确保调用方即使忘记关闭也不会丢数据 |
| `child_locked_count` per PackStruct | Directory safety: inc on file handle creation, dec on unlock; delete/erase blocked when > 0 | 目录安全检查：创建文件句柄时递增，解锁时递减；计数>0 时阻止删除/擦除 |
| Delete vs Erase as separate APIs | Delete is fast (metadata-only I/O, GC data without overwrite); Erase overwrites every byte on disk before removal | 删除快速（仅元数据 I/O，不覆写数据）；擦除在移除前覆写磁盘上所有字节 |
| DoD 5220 writes each pass to disk | All three passes (0x00, 0xFF, random) perform independent disk writes — not just in-memory buffer churn | 三次覆写全部独立写入磁盘，非仅在内存中操作缓冲区 |

### Overall / 总体

| Decision | Rationale | 理由 |
|---|---|---|
| Binary + library crate split | CLI-only code stays in binary crate; reusable logic separated | CLI 专属代码与可重用逻辑分离 |
| Crate-name-qualified paths in command.rs | `command.rs` is in binary crate, not the library | command.rs 在二进制 crate 中，crate:: 无法解析到库模块 |
| `PackFileError` impls `From` both ways | Enables `?` operator + Read/Write/Seek trait impls | 支持 `?` 操作符和标准 trait 实现 |
| Bilingual comments throughout | Chinese developer, English code; comments in both languages | 中英双语注释，方便中文开发者阅读 |
